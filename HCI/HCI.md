# 노드 및 서비스 구성
## 서비스
- PCS (POPCON Cloud Service)d
	- 웹 기반 클라우드 관리 서비스
- PVS (POPCON Virtual Storage)
	- ceph 기반 팝콘 분산 스토리지 서비스
- **PSM (Popcon Service Manager)**
	- k3s pod로 배포되는 팝콘 호스트 관리/클러스터 설치 서비스
- PCM (PCS 관련 데몬, `/usr/sbin/pcm`)
	- PCS 기능을 구현하는 프로세스(도구)
	- pcm-cli 등으로 클러스터,라이센스, 설정을 관리하는 실행파일/명령행 도구

- PSM 실제 구성

③ (사람이 직접) 브라우저로 PSM-UI 접속 → 호스트 등록/네트워크 설정/클러스터 생성 버튼 클릭

# 인스턴스 생성 관련 용어
## 부팅 순서 / 디스크
- 시스템 디스크
	- 인스턴스의 OS가 설치되는 부팅 디스크
		- 부팅 가능한 볼륨 / 빈 볼륨 / 이미지 
	- 설치 과정 없이 인스턴스가 바로 부팅됨, qcow2와 같은 형식
	- 대부분의 리눅스 배포판(클라우드 이미지) 방식
- 데이터 디스크
	- 시스템 디스크 외 추가로 붙이는 저장공간
	- 두 가지 방식
		- 빈 볼륨
		- 기존 볼륨 - 프로젝트에 이미 존재하는 볼륨
- 디스크 버스
	- VM의 가상 하드웨어에 디스크가 어떤 방식 (컨트롤러/버스)로 연결되는지 나타내는 설정
		- libvirt XML의 `<target bus="..."/>` 에 해당
	- 관련 일감 : #182322 (디스크 버스 수정 기능 개발)
		- 지원타입: ide, fdc, scsi, virtio, usb, xen, uml, sata (기본값: virtio)
		- 인스턴스가 종료 중일 때만 변경 가능
		- 컨트롤러별 슬롯 수 제한 존재 (IDE는 최대 4개까지 설정 가능)
		- CD-ROM은 디스크버스가 IDE로 고정
- CD-ROM 드라이브
	- **ISO 이미지를 마운트하기** 위한 가상 광학 드라이브
		- 디스크 버스가 IDE로 하드코딩 되어 있음
		- OS가 아직 설치되지 않은 상태
```
IDE: hdd나 cd-rom같은 저장장치를 메인보드에 연결할 때 쓰던 표준
오래되고 단순한 규격이라 운영체제가 별도 드라이버 설치 없이 잘 인식함 
```
- 부팅 가능한 볼륨
	- OS 이미지 데이터가 담겨 있어서 그 자체로 부팅이 가능한 볼륨
	- 다른 인스턴스의 OS 디스크였던 볼륨을 그대로 부팅 디스크로 재사용 하는 개념
	- #182374
		- 볼륨의 `volume_image_metadata["hw_firmware_type"]` 값을 확인해서 펌웨어를 결정하는 로직 존재
		  -> 부팅 가능한 볼륨은 이전의 메타데이터를 가지고 있음
- 부팅 순서
	- 부팅순서: 인스턴스에 연결된 여러 개의 디스크/CD-ROM 중 어디서부터 부팅을 시도할지 정하는 우선순위 
	  물리 서버 BIOS의 부팅 장치 순서와 동일 개념
	- 부팅 순서대로 진행, 빈 슬롯이면 다음으로 넘어간다 (cd-rom - 시스템 디스크)
	  부팅 순서는 변경 가능
	- 수동 부팅 디바이스 선택 - 콘솔에서 `Ctrl+Alt+Del` → 화면 전환 직후 `ESC` → "Select boot device" 화면으로 자동 순서를 무시하고 원하는 디바이스로 강제 부팅 가능
	- 설치 과정
		- CD-ROM의 iso 부팅해서 설치
		  설치 프로그램이 OS파일들을 시스템 디스크(빈 디스크)에 복사/설치
		  시스템 디스크에 OS+부트로더가 생성됨
		  이후에는 시스템 디스크에 있는 OS로 부팅함
```
시스템 디스크 / iso / 부팅가능한볼륨 차이:
시스템 디스크 - OS가 이미 설치되어 있는 이미지, 실제 파일시스템+부트로더+OS
-> 매번 부팅할 때 사용하는 디스크

iso - 설치 프로그램, 설치 파일
-> 설치 화면에서 사용자가 직접 설치해야 함 (1회성)

부팅 가능한 볼륨:
이미 스토리지에 존재하던 볼륨, 즉 디스크에 있던 내용 그대로 부팅 가능
-> 생성 시점에 대한 차이라서 시스템 디스크와 서로 바꿔서 사용해도 됨 (#126188 (인스턴스 이미지 생성 가이드))
```

- 보안 부팅
	- UEFI 펌웨어일 때 제공하는 기능
	- 서명되지 않거나 변조된 부트로더/OS 실행 차단
	- 호스트가 `COMPUTE_SECURITY_UEFI_SECURE_BOOT` 지원 필요
		- uefi 사용 + 보안부팅은 사용 안할 수도 있음, 보안부팅 사용 시 오히려 오래된 리눅스 배포판 등은 사용 불가할 수도 있음
- UEFI를 사용하기 위해서는 머신타입이 반드시 q35여야 한다.


## 머신 타입
- 가상머신이 어떤 가상 메인보드/칩셋으로 동작하는지 정의하는 칩셋
	- 인스턴스의 가상 칩셋
	- 일반적으로 x86_64 환경에서는 2개, (+특수 환경 1개) 정도로 지원함
- QEMU가 지원하는 머신타입
	- x86_64 아키텍처 기반: 
		- i440fx 계열: PCI버스 기반(구세대), 90년대 후반 메인보드 애뮬레이션 
		- q35계열: PCIe 버스 기반, 2000년대 후반 메인보드 애뮬레이션
	- 다른 cpu 아키텍처(ARM 등)은 virt 라는 네임 사용

### 메인보드 칩셋이란?
- CPU와 나머지 부품들 (메모리, 그래픽카드, 저장장치, USB, 네트워크 등) 사이에서 데이터가 오가는 통로를 관리하는 역할
	- CPU는 다른 부품과 직접 대화할 수 없음
	  ex. SATA 디스크에서 데이터 읽어오기, usb포트 인식, PCIe 슬롯에 그래픽 카드 연결되는 방식 등은
	  메인보드 칩셋이 대신 처리
	-
